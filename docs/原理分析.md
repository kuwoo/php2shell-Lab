## 1. 漏洞概述

**php2shell** 是 PHP 核心（`session` 模块）里的一组漏洞，官方编号：

- CVE-2026-109618
- CVE-2026-109619

核心特征：

| 维度 | 内容 |
|------|------|
| 类型 | 无需认证（pre-auth）的远程代码执行（RCE） |
| 评分 | CVSS 4.0 **9.2（严重）** |
| 根因 | `session.upload_progress` 处理器对上传文件名的处理 |
| 影响版本 | PHP **5.4.0 ~ 8.5.11**（横跨十几年） |
| 修复版本 | 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12（2026-10-21 14:00 UTC 发布） |

公开研究 [ikow/php2shell-poc](https://github.com/ikow/php2shell-poc) 把它拆成三条攻击链（A / B / C），本仓库只实现**最直观、最可靠、不依赖内存破坏的 Chain A**。

## 2. 前置知识

### 2.1 PHP 会话是怎么存文件的

PHP 默认用文件保存会话。假设会话 ID 是 `abc123`，默认配置下会话数据存在：

```
/tmp/sessions/sess_abc123
```

文件内容是 `键名|序列化数据`，例如：

```
login_user|s:5:"admin";csrf_token|s:32:"...";
```

关键点：**这个文件是普通文本文件**。只要你知道会话 ID，就能拼出它的完整路径。

### 2.2 `session.upload_progress` 是干嘛的

从 PHP 5.4 开始，PHP 内置了「上传进度」功能（默认开启）：

- 当收到一个 multipart 表单上传时，PHP 会在会话里记录上传进度；
- 前端可以轮询这个进度来显示进度条。

它往会话里写的数据长这样（简化）：

```
upload_progress_<名字>|a:5:{
    start_time; content_length; bytes_processed; done;
    files: [ { field_name, name, tmp_name, error, ... } ]
}
```

其中：

- `upload_progress_<名字>` 里的「名字」来自表单里的 `PHP_SESSION_UPLOAD_PROGRESS` 字段；
- `files[].name` 就是**你上传文件的原始文件名**。

## 3. 漏洞根因

一句话：

> **PHP 把「上传文件的文件名」当成普通文本，原样写进了会话文件，没有做任何过滤。**

而会话文件是 PHP 会去解析执行的普通文本。于是：

- 如果文件名是 `shell.php`，没事；
- 如果文件名是 `<?php system('id'); ?>`，这段 PHP 代码就被原样写进了会话文件。

一旦有办法让 PHP 去「执行」这个会话文件（比如应用存在 LFI 并 include 了它），里面的 `<?php ... ?>` 就会被当成 PHP 代码执行 → **远程代码执行**。

这解释了为什么叫 **php2shell**：把 php 会话文件变成一个 shell。

## 4. Chain A 完整攻击链

Chain A 需要两个条件配合：

1. `session.upload_progress` 开启（**默认就是开的**）；
2. 目标应用存在一个**本地文件包含（LFI）**漏洞。

完整流程分三步：

### 第 1 步：固定会话 ID

攻击者先选定一个会话 ID（比如 `sess_abc123`）。为了让后面能精准包含会话文件，他必须让 PHP 用这个 ID 写会话文件。

### 第 2 步：上传 + 注入文件名

攻击者发一个 multipart POST，里面包含：

- 一个 `PHP_SESSION_UPLOAD_PROGRESS` 字段（触发上传进度记录）；
- 一个 `PHPSESSID` 字段（固定会话 ID，见第 5 节）；
- 一个文件，**文件名是 PHP 代码**：

```
<?php echo 'RCE OK'; system($_GET['c']); ?>
```

PHP 处理上传时，把这个文件名原样写进会话文件：

```
/tmp/sessions/sess_abc123
```

文件内容变成：

```
upload_progress_chainA|a:5:{...s:4:"name";s:48:"<?php echo 'RCE OK'; system($_GET['c']); ?>";...}
```

现在，一段「活」的 PHP 代码已经躺在了会话文件里。

### 第 3 步：LFI 包含会话文件

攻击者利用应用的 LFI：

```
http://target/index.php?page=/tmp/sessions/sess_abc123&c=id
```

`include('/tmp/sessions/sess_abc123')` 会把这个文件当 PHP 解析：

1. `<?php` 之前的 `upload_progress_chainA|a:5:{...` 被原样输出（这就是 PoC 输出里那段乱糟糟的前缀）；
2. `<?php echo 'RCE OK'; system($_GET['c']); ?>` 被执行 → 输出 `RCE OK` + `id` 的结果；
3. `?>` 之后的序列化尾巴继续被输出。

于是攻击者拿到了命令执行，身份就是 PHP 进程的运行用户。

> `poc.py` 里做的正是这三步：先注入，再 LFI 包含，最后把输出里的序列化前缀 `split` 掉、只显示命令结果。

## 5. 关键细节一：PHPSESSID 绕过 use_only_cookies

正常情况下 PHP 只从 **Cookie** 里取会话 ID（`session.use_only_cookies=1`，这是默认且是安全配置）。攻击者没法给受害者设 Cookie，似乎就固定不了会话 ID。

但 php2shell 的一个关键点是：**`session.upload_progress` 处理器会接受 POST body 里直接传的 `PHPSESSID`**，从而绕过 `use_only_cookies`。

效果就是**会话固定（session fixation）**：

- 攻击者在请求 body 里写 `PHPSESSID=abc123`；
- PHP 用 `abc123` 作为会话 ID 写进度；
- 攻击者**提前知道**会话文件路径就是 `/tmp/sessions/sess_abc123`；
- 于是可以直接用 LFI 去包含它。

`poc.py` 里为了稳妥，body 和 Cookie **都**带了同一个 `PHPSESSID`（双保险）。

---

## 6. 关键细节二：cleanup 与竞态窗口

`session.upload_progress.cleanup` 控制「上传结束后要不要清掉进度数据」：

- **默认 `cleanup=On`**：上传一结束，PHP 就把 `upload_progress_*` 这段从会话里删掉。也就是说注入是**转瞬即逝**的。
- 真实攻击者怎么应对？**打竞态**：传一个很大的文件（上传慢），在文件还在上传、进度数据还没被清理的窗口里，用**并发请求**去包含会话文件。

本靶场为了让你**每次都能确定性成功**，把 `cleanup` 设成了 `Off`（见 `php.ini`），这样注入会一直留在会话文件里，不用打竞态。原理和真实攻击完全一致，只是把「需要竞争」简化成了「必然命中」。

## 7. 三条攻击链对比

公开研究把 php2shell 拆成三条链，难度和依赖完全不同：

| 链 | 原理 | 复杂度 | 依赖 | 本仓库 |
|----|------|--------|------|--------|
| **Chain A** | 文件名注入 + 应用 LFI → RCE | 低，100% 可靠 | 应用要有 LFI | ✅ 实现 |
| **Chain B** | `var_destroy` 释放后使用（UAF）内存破坏 → RCE | 高 | 应用 `unserialize` 会话数据（ASAN 验证） | ❌ 不提供 |
| **Chain C** | 会话 handler 不匹配 + POP gadget（反序列化利用） | 中高 | 特定多目录 + 反序列化 gadget | ❌ 不提供 |

说明：

- **Chain B** 才是那个 9.2 分「内存破坏」的狠角色（UAF），但它需要目标反序列化攻击者可控的会话数据，且原仓库只有 ASAN 崩溃验证脚本、没有开箱即用的利用；把 UAF 做成稳定 RCE 属于武器化利用，本仓库不提供。
- **Chain C** 依赖特定应用里的反序列化 gadget，属于「应用层组合拳」。

本仓库选 **Chain A**：原理最清晰、最能讲清楚「php2shell 到底是什么」，也最适合教学。

## 8. 靶场里的两处故意简化

为了让「一键复现」，本靶场做了两处简化（都不改变漏洞本质）：

1. **`session.upload_progress.cleanup = 0`**（`php.ini`）——让注入确定性留存，省去打竞态的并发脚本（见第 6 节）。
2. **故意提供一个 LFI 端点**（`app/index.php` 里的 `?page=...` → `include`）——因为 Chain A 的前提就是应用要有 LFI。

这两点都已在代码和 README 里标注，避免读者误以为「真实环境也这么简单」。

## 9. 关于权限：为什么是 www-data 而不是 root

很多读者会问：RCE 了是不是就「拿下服务器」了？答案是——**取决于 PHP 进程以什么身份运行**。

本靶场（也是绝大多数生产环境）里：

- Apache 主进程以 root 启动（要绑定 80 端口），但**一启动就 fork 出子进程并降权到 `www-data`**（由 `APACHE_RUN_USER`/`APACHE_RUN_GROUP` 决定）；
- mod_php 跑在 Apache 子进程里，所以 PHP 也以 `www-data` 运行；
- 因此 php2shell 拿到的命令执行身份就是 `www-data`，**不是 root**。

顺带一个冷知识：Apache 甚至**直接拒绝以 root 服务**——它编译期带 `BIG_SECURITY_HOLE` 保护，把 `User` 设成 `root` 会拒绝启动。这也是为什么本靶场没有做「root 版」：那需要靠额外的本地提权漏洞，属于另一类问题。

**结论**：php2shell 给的是 web 用户（www-data）。从 www-data 到 root 是「本地提权」的范畴（内核漏洞、SUID 程序、配置错误等），与本 CVE 无关，本仓库也不涉及。

## 10. 如何检测

除了直接打（在授权目标上），还可以用**黑盒侧信道**判断目标是否开启了 `session.upload_progress`：

- 向目标发一个触发上传进度的请求；
- 观察响应头里是否**被动出现了 `Set-Cookie: PHPSESSID=...`**（因为 upload_progress 会自动启动一个会话，PHP 会下发会话 Cookie）。

这个「请求本没带会话、响应却 Set-Cookie」的副作用，可以作为一个**非侵入式**的检测信号。但要注意：生产环境常被 WAF / CDN / UA 校验 / 静态站干扰，本地靶场里的现象不能直接照搬到真实站点。

## 11. 如何修复与缓解

按优先级：

1. **升级到修复版本**（最根本）：8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 及以上。
2. **临时缓解**：设置 `session.upload_progress.enabled = 0`。
   - 注意：这能**减少 Chain A 的注入面**，但**不能完全修复** Chain B 的 UAF / 序列化器泄露问题，官方补丁仍是必须的。
3. **应用层加固**：
   - 修掉 LFI（不要 `include` 用户可控路径，用白名单）；
   - 禁止从 POST body 接受 `PHPSESSID`；
   - 会话文件放到不可被 web 进程直接包含的位置。
